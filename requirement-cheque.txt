-------------------------------------------------------------------------------
1. PURPOSE / ONE-LINER
-------------------------------------------------------------------------------
Managers receive physical cheques from dealers, scan/upload them. The system uses
OCR + AI to auto-extract the cheque details and pre-fill a form. The manager
reviews/edits and submits for admin approval. The admin approves (cheque becomes
"submitted"), later records when it was presented to the company's bank, and
finally marks it "passed" (cleared) or "bounced". The module tracks each cheque
through this lifecycle and gives a reconciliation view of what is outstanding,
presented, cleared, or bounced.

This is a CHEQUE-TRACKING + APPROVAL workflow with AI-assisted data entry. It is
financially independent of the HR/attendance/payroll data (dealers ≠ employees).

-------------------------------------------------------------------------------
2. ACTORS & ROLES (reuse existing auth: admin / manager)
-------------------------------------------------------------------------------
- MANAGER: uploads scanned cheque images; the system pre-fills fields; the
  manager reviews/edits and SUBMITS FOR APPROVAL. Cannot approve. Cannot change a
  cheque once approved.
- ADMIN: reviews submitted cheques in an approvals queue; APPROVES (→ "submitted")
  or REJECTS (with reason, back to the manager). After approval the admin records
  bank PRESENTATION and the final OUTCOME (passed/bounced). Sees the full
  reconciliation dashboard.
- (Open) whether managers are scoped to only their own uploaded cheques / their
  groups, or see all — see §12.

-------------------------------------------------------------------------------
3. CHEQUE LIFECYCLE (state machine)
-------------------------------------------------------------------------------
States (proposed):
  draft         -> manager uploaded; OCR/AI extraction done; manager editing
  pending       -> manager submitted for admin approval (locked from manager edit)
  rejected      -> admin rejected (reason); returns to manager to fix -> draft
  submitted     -> admin approved (figures frozen; cheque accepted into the system)
  presented     -> admin recorded date it was deposited/presented to OUR bank
  passed        -> admin recorded the cheque cleared (with clear date)
  bounced       -> admin recorded the cheque bounced (with reason + date)

Transitions & who:
  (manager) upload+extract ......... -> draft
  (manager) edit fields ............ draft -> draft
  (manager) submit ................. draft -> pending
  (admin)   reject(reason) ......... pending -> rejected -> (manager) -> draft
  (admin)   approve ................ pending -> submitted
  (admin)   record presented(date, our-bank-account) .. submitted -> presented
  (admin)   mark passed(date) ...... presented -> passed        [terminal]
  (admin)   mark bounced(reason,date) presented -> bounced      [terminal]
  (admin, open) can a bounced cheque be re-presented? -> §12

Notes:
- Only admin advances submitted->presented->passed/bounced.
- Approval "freezes" the extracted/edited field values (like payroll snapshotting).
- Every transition is written to the audit log (actor, before/after, reason).

5. FIELD EXTRACTION PIPELINE (OCR + AI) — the heart of the feature
-------------------------------------------------------------------------------
Goal: on upload, auto-fill as many fields as possible; manager corrects the rest.
The extraction MUST degrade gracefully (never block the manager; manual entry is
always possible; AI quota exhaustion must not break the flow).

INPUT: mostly SCANNED PDF (+ jpg/png). PDFs are rasterized per page to an image FIRST
(client-side via pdf.js), because both the OCR stage and the AI vision endpoint work on
images. One cheque per page (assumed) → one draft per page.

Design principle (per your steer): "OCR first, then AI; AI is limited quota."
Proposed two-stage, degrade-gracefully pipeline:

  STAGE 1 — OCR (always available, unlimited, cheap):
    - Run an OCR engine on the cheque image to get raw text + the MICR line.
    - Reliable for PRINTED fields: cheque number, MICR code, bank name, IFSC,
      account number (printed), amount-in-figures IF printed.
    - Weak on HANDWRITING (date, payee, amounts are usually handwritten on cheques).
    - Candidate engines (OPEN §12): Tesseract (free, local), or a cloud OCR
      (Google Vision / AWS Textract / Azure) which handles handwriting far better
      but costs per page.

  STAGE 2 — AI vision model (accurate, LIMITED QUOTA, via the LLM gateway):
    - Send the cheque image to the AI vision model with a strict JSON schema of the
      cheque fields; it returns all fields (including handwritten) as validated JSON.
    - This is where quota is a concern → use the multi-LLM GATEWAY (see §6) so that
      when the primary model's quota is exhausted, it fails over to another.
    - If ALL AI providers are exhausted/unavailable → fall back to Stage-1 OCR
      pre-fill only (+ manual entry). Record extraction_source accordingly.

  MERGE: prefer AI values where present & confident; fill gaps from OCR; leave the
  rest blank. Store per-field source/confidence so low-confidence fields can be
  visually flagged for the manager to double-check.

  (OPEN §12: is the pipeline truly two-stage OCR→AI, or is the AI vision model the
  PRIMARY extractor with OCR only as the offline/quota fallback? The vision LLM
  actually does OCR+parse in one step and handles handwriting best, so "AI primary,
  OCR fallback" may be more accurate — but "OCR first" is your stated preference.
  Needs a decision — see §12.)

MANUAL OVERRIDE: every field is editable by the manager before submit, regardless
of how it was filled. Low-confidence / unfilled fields are highlighted.

6. AI / OCR ARCHITECTURE — reusing the S9 LLM GATEWAY
-------------------------------------------------------------------------------
You already have a multi-LLM gateway at:
  ~/Desktop/projects/EAGv3/S9SharedCode/llm_gatewayV9/   (FastAPI, Python 3.11)

What it gives us (directly relevant):
- Endpoint POST /v1/vision : { image (base64 data-url or https URL), prompt,
  schema (JSON schema), schema_name, provider?, max_tokens, temperature } ->
  ChatResponse with .parsed = validated JSON object. It routes to a VISION-capable
  provider, and VALIDATES output against the schema with one corrective retry.
- Providers wired: Gemini (the vision worker), NVIDIA, Groq, Cerebras, OpenRouter,
  GitHub Models, Ollama. Vision today = Gemini (and possibly gpt-4.1-mini via GitHub).
- QUOTA-AWARE FAILOVER (exactly the concern you raised): before each call a provider
  is skipped if it's over RPM/RPD/TPM or in a backoff window; on a 429/quota error
  the provider is put in cooldown (quota/rpm -> 60s, per-day -> 3600s) and the next
  provider is tried; if all are exhausted -> HTTP 503. Per-provider limits are
  hardcoded and tunable. There's also a SQLite call log + per-agent cost rollup.
- No built-in OCR (Tesseract). It does OCR through the vision LLM. So "Stage 1 OCR"
  (if we want a non-LLM OCR) is a SEPARATE component we add.

Integration options (OPEN §12 — pick one):
  (A) RUN THE GATEWAY AS A PYTHON SIDECAR the Next.js app calls over localhost.
      - Deploy llm_gatewayV9/ (uvicorn on :8109) next to the app (Lightsail box or a
        small separate box). Set provider API keys in its .env. Our server actions
        POST the cheque image to /v1/vision with the cheque JSON schema.
      - Pros: reuse routing/failover/validation/cost-ledger as-is; least AI code in
        our app. Cons: adds a Python runtime (~150-250MB) to the 1GB Lightsail box;
        gateway loads its .env from the PARENT dir (deploy gotcha); no auth on its
        HTTP surface (keep it bound to localhost / add a shared secret).
  (B) PORT THE ROUTING LOGIC TO NODE. The valuable IP is ~150 lines (rate-state
      gate + error→cooldown backoff map + failover loop). Reimplement in TS around
      provider SDKs (Gemini etc.). Pros: all-Node, no Python; Cons: we re-own/maintain
      the routing + must add each provider adapter.
  (C) SINGLE CLOUD DOCUMENT-AI (no gateway): e.g. Google Document AI / AWS Textract
      "expense/id" style or a single vision API with a paid quota. Simplest, but
      costs per page and drops the multi-model free-tier fallback you want.

OCR-engine placement (if we keep a non-LLM OCR Stage 1):
  - Tesseract via tesseract.js (Node, runs in the app) — free, no extra service.
  - Or pytesseract in the Python sidecar (co-located with the gateway).
  - Or a cloud OCR API.

  - "Upload cheques" — BULK UPLOAD IS A CORE REQUIREMENT (C3 = YES):
    * INPUT IS MOSTLY PDF (scanned copies), plus images (jpg/png). Accept both.
    * PDF handling: each PDF is RASTERIZED per page into an image before OCR/AI (the
      vision endpoint takes an image, not a PDF). Do this CLIENT-SIDE (pdf.js in the
      browser renders each page to a canvas → image) — fits extract-and-forget (nothing
      hits the server but the transient page image) and needs no server PDF tooling.
      Rasterize at a legible DPI (~150–200) for OCR/AI accuracy; images aren't stored.
    * A multi-page PDF is treated as ONE CHEQUE PER PAGE → N drafts from an N-page PDF.
      (OPEN §12 C5: is it always exactly one cheque per page, or can a page hold 2+
      cheques scanned together? The latter needs page→region splitting.)
    * Drag/drop or select MANY files at once — a batch may be many single files AND/OR
      one big multi-page PDF (e.g. a 50-page scan = 50 cheques). Target ~50–100/batch.
    * The browser holds the pages/images (not the server — extract-and-forget) and sends
      each through extraction: OCR immediately, then AI throttled to the ~15 rpm limit. A
      progress indicator shows "extracted X of N"; each finished cheque becomes an
      editable DRAFT row/card (fields from §4), low-confidence/blank fields highlighted.
    * Because images aren't stored, extraction runs during this session. Each cheque's
      fields are SAVED as a draft as soon as extracted, so partial progress survives if
      the manager stops (the un-extracted, un-saved images are simply lost → re-upload;
      the manager still holds the physical cheques).
    * The manager reviews/edits each draft, then submits — individually OR "Submit all"
      (bulk submit the reviewed drafts for approval). Per-cheque status chip.
    * (Optional) per-cheque "Re-extract"/retry AI while the image is still in the browser.
  - "My cheques": list of the manager's cheques with status + filters + bulk actions.

ADMIN (bulk-friendly): the approvals queue should allow selecting multiple pending
cheques and approving/rejecting in bulk (reject still needs a reason).

ADMIN features (in the existing ONE approvals-style flow, no extra tabs where
possible — you prefer folding into existing queues):
  - "Cheque approvals": queue of PENDING cheques → view image + fields → Approve or

  - "Bank tracking": SUBMITTED cheques → record Presented(date [+ our bank account]);

  - "Reconciliation dashboard": totals & lists by status — outstanding (submitted,

9. NON-FUNCTIONAL / CONSTRAINTS
-------------------------------------------------------------------------------
- Images are NOT stored (extract-and-forget) → no image storage/retention/privacy
  surface at all. The transient image lives only in memory/temp during extraction and
  the manager's same-session review, then is dropped. Extracted DATA still contains
  sensitive values (account no, MICR) → protect the cheques table via RLS as usual.
- Resilience: AI quota exhaustion or gateway down must NOT block uploads — always
  allow manual entry; extraction is best-effort/async.
- Volume: 50–100 cheques/day. AI DAILY quota is fine (Gemini free ~1000/day), but the
  ~15 rpm limit means batch uploads must be QUEUED/THROTTLED so extraction respects the
  rate limit. Since the image isn't kept, extraction happens IN THE UPLOAD SESSION
  (OCR immediately; AI a moment later) and the manager reviews before the image is
  dropped — a large batch is processed a few at a time with visible progress.
- Accuracy: cheques vary hugely by bank; expect the manager to correct ~some fields.
  Amount + cheque number + date accuracy matter most (money). Never auto-submit;
  always human-reviewed before "submitted".
- Cost: prefer the gateway's free-tier models; if a paid cloud OCR is chosen, note
  per-page cost.
- Latency: extraction a few seconds/cheque; show a spinner / process async per image.
- The app is currently HTTP-only on Lightsail — add HTTPS before real cheque data.
